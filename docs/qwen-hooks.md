# Хуки Qwen Code

Хуки Qwen Code - это механизм выполнения скриптов в определённые моменты сессии работы с ИИ-агентом. В Infinite Brain OS хуки используются для автоматической проверки соблюдения правил проекта.

## Расположение хуков

Хуки расположены в директории `.qwen/hooks/`:

```
.qwen/hooks/
├── README.md          # Основная документация по хукам
└── [скрипты хуков]    # Wrapper-скрипты для конкретных событий
```

## Архитектура хуков

### Трёхслойная архитектура

1. **Слой хуков (`.qwen/hooks/`)** - тонкие wrapper-скрипты, специфичные для Qwen Code
2. **Слой проверок (`_system/checks/`)** - портируемые скрипты проверок, используемые несколькими системами
3. **Слой правил (`entities/rules/`, `_system/`)** - документация намерений и рациональностей

### Принцип "тонких обёрток"

Хуки остаются тонкими обёртками. Основная логика проверок живёт в `_system/checks/`, чтобы одни и те же скрипты могли использоваться:

- Хуками Qwen Code
- Скриптом `_system/validate.sh` (паритет между средами исполнения)
- Прямым вызовом агентом или оператором

## Доступные хуки

### session-start.sh (если поддерживается Qwen Code)

Запускается при начале сессии Qwen Code.

**Что делает:**
- Запускает `_system/checks/session-ledger-status.sh` 
- Проверяет количество активных сессий
- Ищет устаревшие сессии (старше 3 дней)
- Выводит напоминание о дисциплине сессий

**Цель:** Напомнить о необходимости регистрации сессий в `sessions/` слое.

### post-write-lint.sh (если поддерживается Qwen Code)

Запускается после каждой записи файла Qwen Code.

**Что делает:**
- Извлекает путь к файлу из JSON события хука
- Если файл является markdown файлом репозитория, запускает `_system/checks/node-lint.sh`
- Проверяет:
  - Наличие frontmatter
  - 8 обязательных ключей узла
  - Запрет на тире em и en
  - Текст-заглушку
- Использует те же исключения путей, что и `validate.sh`

**Цель:** Обеспечить мгновенную обратную связь о качестве создаваемых узлов.

### stop-check.sh (если поддерживается Qwen Code)

Запускается при завершении сессии Qwen Code.

**Что делает:**
- Запускает `_system/checks/uncommitted-work-check.sh` (сводка рабочего дерева)
- Запускает `_system/checks/adapter-sync-check.sh` (проверка синхронизации адаптеров)
- Выводит результаты как напоминания в конце сессии

**Цель:** Напомнить о несохранённой работе и рассинхронизации адаптеров.

## Регистрация хуков

Хуки регистрируются в файле конфигурации Qwen Code (когда Qwen Code поддерживает хуки):

```json
{
  "hooks": {
    "sessionStart": ".qwen/hooks/session-start.sh",
    "postWrite": ".qwen/hooks/post-write-lint.sh",
    "sessionStop": ".qwen/hooks/stop-check.sh"
  }
}
```

## Политика "только предупреждения"

**Все хуки в этом слое работают в режиме "только предупреждения":**

1. **Всегда exit code 0** - хуки никогда не блокируют операции
2. **Информационный вывод** - результаты проверок выводятся как информация
3. **Обратная связь вместо блокировки** - для хуков PostToolUse любые нарушения передаются модели как обратная связь без отмены записи

### Усиление проверок

Перевод любой проверки в режим блокировки - это решение оператора, которое регистрируется в `_system/enforcement-tiers.md`. Этот файл также объявляет уровень принуждения для каждого нумерованного правила `_system`.

## Добавление нового хука

### Шаг 1: Создание логики проверки

Поместите логику проверки в `_system/checks/` как самодостаточный скрипт и задокументируйте его в README этой папки.

### Шаг 2: Создание тонкой обёртки

Добавьте тонкую обёртку в `.qwen/hooks/`, которая делегирует выполнение скрипту из `_system/checks/`.

### Шаг 3: Настройка прав доступа

Сделайте оба скрипта исполняемыми:
```bash
chmod +x _system/checks/your-check.sh
chmod +x .qwen/hooks/your-hook-wrapper.sh
```

### Шаг 4: Регистрация хука

Зарегистрируйте обёртку в `.qwen/settings.json` под правильным событием.

### Шаг 5: Декларация в enforcement-tiers.md

Объявите проверку в `_system/enforcement-tiers.md` (уровень, покрытие правил, политика "только предупреждения").

### Шаг 6: Тестирование

Протестируйте хук, симулируя событие.

## Взаимосвязь с правилами

Хуки обеспечивают механическое выполнение:

1. **Правил в `entities/rules/`** (предоставляются Qwen Code через `.qwen/rules/`)
2. **Нумерованных контрактов в `_system/`**

### Разделение ответственности:

- **Файл правил**: документирует намерения и рациональности
- **Скрипт проверки**: механизм выполнения
- **`_system/enforcement-tiers.md`**: реестр, указывающий, какие правила покрыты механически, а какие остаются на усмотрение

## Пример: Хук проверки frontmatter

### Скрипт про��ерки (`_system/checks/frontmatter-check.sh`):
```bash
#!/bin/bash
# Проверяет наличие обязательного frontmatter в markdown файлах

file_path="$1"

# Проверка наличия frontmatter
if ! head -2 "$file_path" | grep -q "---"; then
  echo "WARNING: File $file_path is missing frontmatter"
fi
```

### Обёртка хука (`.qwen/hooks/post-write-lint.sh`):
```bash
#!/bin/bash
# Обёртка для проверки после записи

# Извлечение пути файла из JSON события
file_path=$(echo "$1" | jq -r '.filePath')

# Запуск проверки frontmatter
if [[ "$file_path" == *.md ]]; then
  "$(dirname "$0")/../../_system/checks/frontmatter-check.sh" "$file_path"
fi
```

## Отладка хуков

### Просмотр логов хуков

Хуки Qwen Code обычно выводят информацию в стандартный вывод/ошибки, который можно перенаправить в файл логов.

### Тестирование хуков вручную

Вы можете протестировать хук вручную, симулируя событие:
```bash
# Пример для хука post-write-lint.sh
echo '{"filePath": "test.md"}' | .qwen/hooks/post-write-lint.sh
```

### Проверка exit code

Помните: все хуки должны возвращать exit code 0:
```bash
.qwen/hooks/session-start.sh
echo $?  # Должно быть 0
```

## Миграция с хуков Claude Code

Если вы мигрируете с Claude Code:

1. **Аналогичная структура**: Архитектура хуков сохраняется
2. **Общие проверки**: Скрипты в `_system/checks/` остаются неизменными
3. **Новые обёртки**: Создаются новые обёртки в `.qwen/hooks/`
4. **Обновление конфигурации**: Обновляется файл конфигурации для Qwen Code

## Лучшие практики

1. **Минимальные обёртки**: Хуки должны быть максимально тонкими
2. **Переиспользование кода**: Используйте общие скрипты из `_system/checks/`
3. **Информативность**: Вывод хуков должен быть полезным и конкретным
4. **Ненавязчивость**: Хуки не должны мешать рабочему процессу
5. **Документация**: Каждый хук должен быть задокументирован
